1. Requerimientos Funcionales (RF) y Mockups

Mockup: Gestión de destinos y contenido turístico

Este mockup representa las funcionalidades relacionadas con la consulta y gestión de la información turística. Incluye elementos para mostrar destinos, fotografías, precios, tarifas, información del clima, rutas y otros datos de interés para los turistas.

Abrir Prototipo en Figma
ERF-01.1: Registrar destinos turísticos

Descripción: Permite al administrador u operador ingresar la información básica y detallada de un nuevo punto de interés turístico.

Entrada: Nombre, descripción, ubicación geográfica (coordenadas), categoría y datos de contacto.

Salida: Confirmación de registro exitoso y visualización del destino en el listado administrativo.

Criterio de Aceptación: El sistema debe validar que el nombre no esté duplicado y que las coordenadas sean geográficamente válidas.

ERF-01.2: Gestionar galería fotográfica

Descripción: Herramienta para subir, organizar y eliminar imágenes asociadas a un destino específico.

Entrada: Archivos de imagen (JPG, PNG), títulos de imagen y orden de visualización.

Salida: Galería actualizada visualmente en el perfil del destino.

Criterio de Aceptación: El sistema debe soportar carga masiva y optimizar automáticamente el peso de las imágenes sin perder calidad crítica.

ERF-01.3: Registrar precios y tarifas

Descripción: Definición de los costos de entrada o servicios asociados al destino.

Entrada: Tipo de tarifa (niños, adultos, extranjeros), moneda y valor numérico.

Salida: Tabla de precios actualizada en la ficha del destino.

Criterio de Aceptación: El sistema debe permitir valores decimales y asegurar que los precios sean mayores a cero.

ERF-01.4: Mostrar estado de vías y condiciones de acceso

Descripción: Información actualizada sobre la viabilidad de las rutas de llegada al destino.

Entrada: Estado (Abierta, cerrada, restringida) y notas de observación.

Salida: Indicador visual (tipo semáforo) y texto informativo para el usuario.

Criterio de Aceptación: El estado de las vías debe mostrar la fecha y hora de la última actualización.

ERF-01.5: Mostrar clima en tiempo real

Descripción: Integración con API meteorológica para mostrar las condiciones actuales en la ubicación del destino.

Entrada: Coordenadas del destino (automático) o código de ciudad.

Salida: Temperatura, humedad y estado del cielo.

Criterio de Aceptación: Los datos deben actualizarse con un margen de error no mayor a 30 minutos respecto a la fuente oficial.

ERF-01.6: Categorizar y etiquetar destinos

Descripción: Clasificación de destinos mediante etiquetas (tags) y categorías padre para facilitar la navegación.

Entrada: Nombre de categoría y etiquetas.

Salida: Árbol de categorías actualizado y filtros funcionales.

Criterio de Aceptación: Un destino debe poder pertenecer a múltiples etiquetas pero a una categoría principal.

ERF-01.7: Gestionar temporadas turísticas

Descripción: Configuración de periodos de tiempo (Alta, Baja, Media) para ajustar disponibilidad o precios.

Entrada: Rango de fechas y nombre de la temporada.

Salida: Calendario de temporadas configurado en el sistema.

Criterio de Aceptación: El sistema debe alertar si hay solapamiento de fechas entre temporadas del mismo tipo.

ERF-01.8: Crear rutas turísticas organizadas

Descripción: Agrupación de varios destinos en un itinerario lógico sugerido.

Entrada: Selección de destinos, orden de visita y tiempo estimado.

Salida: Mapa de ruta trazado y lista de paradas secuencial.

Criterio de Aceptación: La ruta debe calcular la distancia total en kilómetros de forma automática.

ERF-01.9: Gestionar contenido por operador (CMS)

Descripción: Panel de control independiente para que los operadores turísticos editen solo su propio contenido.

Entrada: Credenciales de operador, textos descriptivos y actualizaciones.

Salida: Contenido publicado bajo la autoría del operador específico.

Criterio de Aceptación: Un operador no debe tener permisos para editar o eliminar contenido de otros operadores.

ERF-01.10: Registrar historial de cambios de contenido

Descripción: Auditoría de todas las modificaciones realizadas sobre la información de los destinos.

Entrada: Usuario, fecha/hora, campo modificado, valor anterior y nuevo.

Salida: Log de auditoría consultable por administradores.

Criterio de Aceptación: El historial debe ser de "solo lectura" y no permitir borrado manual.

ERF-01.11: Buscar contenido con autocompletado

Descripción: Barra de búsqueda predictiva que sugiere destinos o categorías mientras el usuario escribe.

Entrada: Cadena de texto (mínimo 3 caracteres).

Salida: Lista desplegable de sugerencias coincidentes.

Criterio de Aceptación: El tiempo de respuesta de las sugerencias debe ser inferior a 300ms.

ERF-02.1: Registrar turistas

Descripción: Permite a los visitantes crear una cuenta personal para acceder a funciones interactivas.

Entrada: Nombre completo, correo, país, idioma y contraseña.

Salida: Cuenta creada y correo de verificación enviado.

Criterio de Aceptación: Validar correo único y complejidad de contraseña.

ERF-02.2: Registrar operadores turísticos

Descripción: Registro especializado para empresas o guías que desean publicar contenido y servicios.

Entrada: Nombre de empresa, NIT, teléfono, dirección y documentos de soporte.

Salida: Solicitud de registro en estado "Pendiente de aprobación".

Criterio de Aceptación: Permitir carga de archivos (PDF/JPG) para validación legal.

ERF-02.3: Gestionar autenticación con JWT

Descripción: Implementación de seguridad mediante JSON Web Tokens para manejar sesiones.

Entrada: Credenciales de usuario.

Salida: Access Token y Refresh Token.

Criterio de Aceptación: Expiración tras inactividad y obligatorio para APIs privadas.

ERF-02.4: Recuperar y cambiar contraseña

Descripción: Flujo para restablecer acceso por olvido o seguridad.

Entrada: Correo registrado, nueva contraseña y código de verificación.

Salida: Contraseña actualizada exitosamente.

Criterio de Aceptación: Enlace válido por máximo 1 hora y un solo uso.

ERF-02.5: Gestionar roles y permisos (RBAC)

Descripción: Control de acceso basado en roles para definir qué puede hacer cada usuario.

Entrada: Nombre del rol y matriz de permisos.

Salida: Configuración guardada en base de datos.

Criterio de Aceptación: Retorna error 403 Forbidden si no está autorizado.

ERF-02.6: Gestionar perfil de turista

Descripción: Espacio personal donde el turista actualiza su información y actividad.

Entrada: Foto de perfil, intereses, datos biográficos.

Salida: Perfil actualizado.

Criterio de Aceptación: Permitir eliminar cuenta cumpliendo normativas de protección de datos.

ERF-02.7: Gestionar perfil de operador

Descripción: Panel de administración del operador para mostrar marca y servicios.

Entrada: Logo, descripción, redes sociales y horarios.

Salida: Perfil público actualizado.

Criterio de Aceptación: Notificar cambios en campos críticos al administrador general.

ERF-02.8: Administrar usuarios

Descripción: Módulo exclusivo del administrador para supervisar a todos los usuarios.

Entrada: Filtros de búsqueda, opciones de Bloquear o Activar.

Salida: Lista de usuarios actualizada y logs.

Criterio de Aceptación: Suspensión de cuentas con bloqueo de sesión inmediato.

ERF-03.2: Enviar solicitud de reserva

Salida: Registro en base de datos y notificación al operador.

ERF-03.3: Enviar confirmación de reserva por correo

Entrada: Estado Confirmada y datos del turista/destino.

Salida: Correo HTML con ID, costos y código QR.

Criterio de Aceptación: Enviado en un tiempo menor a 2 minutos.

ERF-03.4: Gestionar estados de reserva

Descripción: Flujo de trabajo para controlar el ciclo de vida de la solicitud.

Entrada: Selección de nuevo estado (Pendiente, Confirmada, Cancelada, Completada).

Salida: Actualización en base de datos y aviso.

Criterio de Aceptación: Exigir motivo obligatorio si se marca como Cancelada.

ERF-03.5: Consultar historial de reservas

Descripción: Listado cronológico de interacciones de reserva.

Entrada: Filtros de fecha y estado.

Salida: Tabla o lista detallada.

Criterio de Aceptación: Turista solo ve sus reservas; operador las de sus destinos.

ERF-03.6: Atender consultas con chatbot

Descripción: Asistente virtual automatizado 24/7 para preguntas frecuentes.

Entrada: Mensaje de texto en lenguaje natural.

Salida: Respuesta automática o transferencia a humano.

Criterio de Aceptación: Tiempo de respuesta inferior a 2 segundos.

ERF-03.7: Enviar notificaciones push y correo

Descripción: Sistema de alertas sobre cambios, promociones o recordatorios.

Entrada: Evento del sistema o campaña de marketing.

Salida: Notificación móvil y/o correo.

Criterio de Aceptación: Opción para activar o desactivar desde el perfil.

ERF-03.8: Gestionar mensajería interna

Descripción: Canal de chat centralizado entre turista y operador.

Entrada: Mensajes de texto y archivos adjuntos.

Salida: Interfaz de chat en tiempo real con historial.

Criterio de Aceptación: Indicar visualmente estado (Enviado, Leído) y hora.

Este mockup representa los elementos de la interfaz relacionados con la seguridad de la plataforma y la protección de la información de los usuarios, incluyendo acciones relacionadas con el acceso y manejo seguro de los datos.

ERF-06.1: Proteger endpoints con JWT

Descripción: Middleware que valida identidad antes de acceder a la API.

Entrada: Bearer Token en encabezados HTTP.

Salida: Acceso concedido o error 401 Unauthorized.

Criterio de Aceptación: Ningún endpoint sensible accesible sin JWT válido.

ERF-06.2: Mitigar ataques (DDoS y fuerza bruta)

Descripción: Defensas contra tráfico malintencionado y robo de cuentas.

Entrada: Frecuencia por IP e intentos fallidos.

Salida: Bloqueo temporal o CAPTCHA.

Criterio de Aceptación: Rate Limiting por usuario único.

ERF-06.3: Cifrar datos en tránsito y reposo

Descripción: Garantizar protección en tránsito y base de datos.

Entrada: Datos sensibles (contraseñas, documentos, teléfonos).

Salida: Hash (BCrypt) y HTTPS/TLS.

Criterio de Aceptación: Contraseñas nunca visibles en texto plano.

ERF-06.4: Cumplir Ley 1581 de protección de datos

Descripción: Adaptación al marco legal colombiano (Habeas Data).

Entrada: Consentimiento por checkbox.

Salida: Registro de autorización y política.

Criterio de Aceptación: Permitir descarga o supresión de datos del usuario.

ERF-06.5: Almacenar documentos de forma segura

Descripción: Gestión protegida de archivos subidos por operadores.

Entrada: Archivos subidos a cloud/servidor.

Salida: Enlaces firmados temporalmente.

Criterio de Aceptación: No indexables por Google ni URL pública directa.

ERF-06.6: Auditar acciones críticas

Descripción: Registros detallados de eventos de alta sensibilidad.

Entrada: Cambios de permisos, borrado de usuarios, tarifas.

Salida: Log inalterable (ID, acción, timestamp, IP).

Criterio de Aceptación: Persistencia mínima de 6 meses protegidos contra modificación.

2. Requerimientos No Funcionales (RNF)

RNF-01: Protección de Datos (Habeas Data)

Descripción: El sistema debe cumplir estrictamente con la Ley 1581 de 2012 de Colombia, asegurando el cifrado de datos sensibles y el consentimiento explícito para el tratamiento de información personal.

RNF-02: Cifrado de Comunicaciones

Descripción: Toda la transferencia de datos entre el cliente (web/app) y el servidor debe realizarse mediante protocolos seguros HTTPS/TLS 1.3.

RNF-03: Seguridad de Contraseñas

Descripción: Las credenciales de acceso deben ser almacenadas utilizando algoritmos de hash robustos (como Argon2 o BCrypt) con "sal" aleatoria.

RNF-04: Tiempo de Respuesta

Descripción: El sistema debe responder a las consultas de búsqueda en menos de 2 segundos bajo condiciones normales de carga.

RNF-05: Capacidad de Usuarios Concurrentes

Descripción: La infraestructura debe soportar al menos 100 usuarios simultáneos sin degradación del servicio, con capacidad de escalado automático en temporadas altas (ej. San Pedro).

RNF-06: Optimización de Activos

Descripción: Las imágenes deben servirse en formatos de última generación (WebP/Avif) y estar optimizadas para reducir el consumo de datos móviles en zonas rurales.

RNF-07: Disponibilidad (Uptime)

Descripción: La plataforma debe garantizar una disponibilidad del 99.9% anual, minimizando las ventanas de mantenimiento programado a horas de bajo tráfico.

RNF-08: Tolerancia a Fallos

Descripción: En caso de caída de un nodo del servidor, el sistema debe ser capaz de redirigir el tráfico a un nodo de respaldo sin pérdida de sesiones activas.

RNF-09: Recuperación ante Desastres (DRP)

Descripción: El tiempo objetivo de recuperación (RTO) ante un fallo total no debe exceder las 4 horas.

RNF-10: Estándar de Accesibilidad

Descripción: La interfaz debe cumplir con las pautas WCAG 2.1 Nivel AA, permitiendo que personas con discapacidades visuales o motoras naveguen la oferta turística.

RNF-11: Diseño Mobile-First

Descripción: Debido a que el turista usa el sistema "en campo", la experiencia de usuario debe estar optimizada prioritariamente para dispositivos móviles antes que para escritorio.

RNF-12: Facilidad de Aprendizaje

Descripción: Un usuario nuevo debe ser capaz de encontrar un destino y contactar a un operador en menos de 3 minutos sin necesidad de tutoriales externos.

RNF-13: Compatibilidad de Navegadores

Descripción: El sistema debe ser compatible con las últimas dos versiones de los navegadores más usados (Chrome, Safari, Firefox, Edge).

RNF-14: Modularidad del Código

Descripción: El software debe estar construido bajo una arquitectura hexagonal, facilitando la actualización de módulos individuales (ej. el chatbot) sin afectar al resto.

RNF-15: Internacionalización (i18n)

Descripción: La arquitectura debe permitir la adición de nuevos idiomas mediante archivos de recursos externos, sin modificar el código fuente.

RNF-16: Precisión de GPS

Descripción: El sistema debe manejar una precisión geográfica de al menos 10 metros para asegurar que las rutas y destinos en el Huila sean localizados correctamente.

RNF-17: Funcionamiento en Baja Conectividad

Descripción: La aplicación móvil debe implementar estrategias de caché agresiva para permitir la visualización de datos previamente cargados cuando el turista entre a zonas con poca señal (cañones o áreas rurales).
